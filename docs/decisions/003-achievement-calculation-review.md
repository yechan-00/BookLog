# 003. 달성률·연속 독서일 계산 위치를 다시 정한다

> 날짜: 2026-11-11 · 작성: 한인웅 · 상태: 제안됨 (팀 검토 중)
> 관련: [`002-achievement-in-db-function.md`](002-achievement-in-db-function.md) (채택되면 대체), `docs/PRD.md` 4.6·9·10장

## Context

- 결정 002는 날짜별 달성 결과를 DB 함수 하나로 계산하고 앱과 관리자 지표가 함께 쓰기로 제안했다. 아직 채택 전이고, 함수는 만들지 않았다.
- 실제 구현은 앱 계산으로 먼저 진행됐다. PR #8에서 `utils/readingPeriod.ts`, `readingStreak.ts`, `weeklyAchievement.ts`, `readingSummary.ts`가 목표 이력과 세션으로 달성 여부·주간 달성률·연속 독서일을 계산하고, 단위 테스트(`utils/readingStats.test.ts`)가 있다. PR #11에서 이력 조회를 요청 한 번으로 바꿨다.
- PRD 4.6의 메모는 "이 계산을 DB 함수로 맞추기 전에는 완료로 두지 않는다"로, 002를 전제로 한다.
- 관리자 대시보드 달성률(ADMIN-02)은 전체 사용자 집계라 SQL이 필요하고, 원문 데이터를 관리자 웹에 넘기지 않는다(PRD 7장).

## Decision (제안)

1. 앱 화면(홈·기록·인사이트)은 지금의 앱 TS 계산을 그대로 쓴다. DB 함수로 옮기지 않는다.
2. 관리자 달성률 지표는 `admin_dashboard_metrics` RPC 안에서 같은 규칙(PRD VIEW-02·03: 목표 요일만, 그날 적용 목표 기준, 목표 날 경계는 `[starts_on, ends_on)`)으로 SQL 집계한다.
3. 두 구현이 어긋나지 않도록, 시드 데이터(`supabase/seed.sql`)의 테스트 계정 하나에 대해 앱 계산 결과와 SQL 결과를 비교해 확인한다. 계산 규칙을 바꿀 때는 두 곳을 같은 PR에서 고친다.
4. 채택되면 002를 "대체됨"으로 표시하고, PRD 4.6 메모·6장 계산값 설명·9장 달성률 정의·10장 접점 4번, `docs/specs/supabase-integration.md`를 이 결정에 맞춘다.

## Alternatives considered

- **002대로 DB 함수로 옮기기**: 계산이 한 벌이라 숫자가 어긋나지 않는다. 하지만 이미 테스트까지 있는 앱 계산을 다시 만들고 화면 연결을 바꿔야 해 12~13주 일정(온보딩·목표, 알림 연결, 관리자 웹)에 부담이 크다.
- **앱 계산만 쓰고 관리자 웹도 원문으로 계산**: 관리자 웹에 세션 원문을 넘겨야 해서 "집계값만 노출" 원칙에 어긋난다.
- **달성 결과를 테이블에 저장**: 목표 수정·세션 저장 때마다 갱신해야 하고, PRD의 "저장하지 않는 계산값" 원칙과 다르다.

## Consequences

- 같은 규칙이 TS와 SQL 두 곳에 있어, 규칙을 바꿀 때 함께 고치지 않으면 앱과 대시보드 숫자가 달라질 수 있다. 3번의 비교 확인으로 줄인다.
- 앱 계산은 이미 단위 테스트가 있어 화면 쪽 변경 없이 VIEW-01~05를 마무리할 수 있다.
- 관리자 SQL 집계는 13주 관리자 웹 작업(한인웅)에서 만든다.
- 한예찬과 합의 전까지는 002·003 모두 "제안됨"이다. 합의 결과에 따라 둘 중 하나를 채택한다.
