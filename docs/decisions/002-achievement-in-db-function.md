# 002. 달성률·연속 독서일을 DB 함수 하나로 계산한다

> 날짜: 2026-11-04 · 작성: 한인웅 · 상태: 제안됨 (팀 검토 중)
> 관련: [`001-supabase-backend.md`](001-supabase-backend.md), `docs/PRD.md` 6·9·10장

## Context

- 달성률·연속 독서일은 저장하지 않는 계산값이고, 앱(기록·홈·인사이트, VIEW-02~05)과 관리자 대시보드 지표(ADMIN-02)가 함께 쓴다.
- PRD 10장 접점 4번은 "달성률 유틸 하나를 함께 쓴다"였지만, 관리자 지표는 admin 전용 집계 RPC(SQL)라서 앱의 TS 유틸을 쓸 수 없다. 그대로 두면 같은 계산을 TS와 SQL로 두 번 구현하게 되어 앱과 대시보드 숫자가 어긋날 수 있다.
- 지금 mock 화면은 `data/selectors.ts`의 TS 함수(`calculateStreak`, `getHomeSnapshot`, `getInsightSnapshot`)로 계산한다.
- 독서 날짜(`reading_sessions.read_on`)는 기기 로컬 날짜로 저장되므로 DB에서도 날짜 경계 문제 없이 계산할 수 있다.

## Decision

1. 사용자의 날짜별 달성 결과(그날 적용 목표, 읽은 양, 달성 여부)를 계산하는 DB 함수를 하나 두고, 달성률·연속 독서일은 이 결과로 계산한다. 함수는 호출자 권한(`security invoker`)이라 RLS가 적용된다.
2. 앱은 이 함수를 `lib/api`로 호출해 표시만 한다. 관리자 집계 RPC는 같은 계산을 전체 사용자에 대해 집계한다.
3. 계산 기준: 목표 요일만 세고, 목표 요일이 아닌 날의 기록은 캘린더에만 표시한다. 연속 독서일은 오늘 목표를 아직 못 채웠으면 어제까지로 센다 (PRD VIEW-02·03).
4. 계산 함수는 한인웅(백엔드), 표시는 한예찬(화면)이 맡는다. 반환 모양을 11주 수요일에 먼저 정하고, 한예찬은 그 모양의 mock으로 화면을 먼저 만든다.

## Alternatives considered

- **앱 TS 유틸 + 관리자 SQL 따로 구현**: 각자 익숙한 언어로 만들 수 있지만, 계산식이 두 벌이라 기준이 바뀔 때마다 둘을 함께 고쳐야 하고 결과가 어긋나기 쉽다.
- **앱 TS 유틸만 쓰고 관리자 웹도 원문 데이터를 받아 계산**: 관리자 웹에 세션 원문을 넘겨야 해서 "집계값만 노출" 요구사항(PRD 7장 개인정보)에 어긋난다.
- **달성 결과를 테이블에 저장**: 조회는 빠르지만 목표 수정·세션 저장 때마다 갱신해야 하고, PRD의 "저장하지 않는 계산값" 원칙과 다르다.

## Consequences

- 기록·홈·인사이트 화면이 이 함수에 의존하므로, 한인웅은 12주 안에 함수를 만들어야 한다.
- 실제 데이터로 바꿀 때 `data/selectors.ts`의 달성률·연속 독서일 계산은 DB 함수 결과로 대체된다. 먼지 단계·책꽂이 배치처럼 앱에서만 쓰는 계산은 지금처럼 TS에 둔다.
- `docs/specs/supabase-integration.md` 5장의 "`calculateStreak` 같은 계산은 `utils/`의 순수 함수로" 부분을 이 결정에 맞춰 고쳐야 한다.
- 계산 SQL은 TS보다 단위 테스트가 번거로우므로, `supabase/seed.sql`의 테스트 데이터로 결과를 확인한다.
