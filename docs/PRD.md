# BookLog MVP PRD (Draft)

> 최종 수정: 2026-11-04 · 작성: 한인웅
> 원본: Claude 문서 「북로그(BookLog) MVP PRD 초안」. 이 파일은 저장소에서 사람과 AI 에이전트가 참고하기 위한 사본이다.

## 1. 개요

북로그는 독서 목표를 하루 단위의 작은 행동으로 나누고, 독서를 시작하고 이어가도록 돕는 모바일 독서 습관 앱이다. 이 문서는 수업 기간(9~15주)에 구현할 MVP의 요구사항을 정의한다.

**배경·문제**

- 성인 연간 종합독서율은 2023년 43.0%에서 2025년 38.5%로 4.5%p 떨어졌다 (문화체육관광부 「2025년 국민 독서실태 조사」).
- 20대 종합독서율은 75.3%로 높지만, 읽고 싶은 마음이 있어도 지속하지 못하는 사용자층이 핵심 타깃이다.
- 기존 독서 앱(북모리, 북적북적)은 기록에 강하지만 독서를 시작·유지·재개하게 만드는 장치가 약하고, 습관 앱(루티너리)은 독서 맥락과 연결되지 않는다.

**해결할 문제 3가지**

| # | 문제 | 해결 방안 |
| --- | --- | --- |
| 1 | 결과 중심 목표라 오늘 얼마나 읽을지 기준이 없음 | 분·페이지 단위 행동 목표 설정 |
| 2 | 습관 유도 기능이 없거나, 기록과 동떨어져 능동적 유도가 없음 | 독서 데이터와 연동한 맥락 알림 + 진행 기반 보상 |
| 3 | 기록 방식이 부담스러움 (구절·생각 직접 타이핑) | 인덱스: 페이지와 짧은 제목으로 기록, 문장은 선택 |

**제품 목표**

1. 부담 없는 목표로 독서를 시작하게 한다.
2. 읽는 동안 집중을 유지하게 한다.
3. 기억하고 싶은 내용을 가볍게 남기게 한다.
4. 과정과 결과를 시각적으로 확인하게 한다.
5. 멈춘 책을 다시 펼치게 한다.

## 2. 대상 사용자와 핵심 시나리오

주 사용자는 독서 의향은 있지만 꾸준히 읽지 못하는 20대이고, 운영자는 관리자 웹으로 서비스 지표와 데이터를 관리한다.

| 사용자 | 설명 | 주요 사용 채널 |
| --- | --- | --- |
| 일반 사용자 (user) | 책을 사 두고도 끝까지 못 읽는 20대 대학생·직장인 | 모바일 앱 (Android·iOS) |
| 운영자 (admin) | 서비스 지표 확인, 회원 이용 정지, 도서 정보 정정 | 관리자 웹 |

**핵심 사용 흐름:** 목표 설정 → 오늘의 독서(타이머) → 기록 → 스트릭 반영 → 인사이트 → 다시 독서

**시나리오 (스토리보드 기준)**

1. **시작하기:** 첫 실행 시 온보딩에서 "하루 15분" 같은 목표와 요일·알림 시간을 정한다. 홈에 오늘의 목표 카드가 나타난다.
2. **책 고르고 읽기:** 책을 검색해 서재에 추가하고 총 페이지를 입력한다. 책 상세에서 독서를 시작하면 집중 독서 모드가 켜지고, 앱을 벗어났다 돌아오면 반응 메시지가 뜬다.
3. **읽으며 남기기:** 읽다가 인덱스(페이지 + 짧은 제목)를 남긴다. 독서를 끝내면 끝 페이지와 한줄평을 입력하고, 다 읽으면 별점·총평으로 완독 처리한다.
4. **기록 확인하기:** 기록 탭에서 캘린더·주간 달성률·연속 독서일을, 인사이트 탭에서 달성률 카드를 본다.
5. **다시 시작하기:** 목표 요일에 읽지 않으면 알림이 온다. 서재에서 오래 안 읽은 책에 쌓인 먼지를 스와이프로 털면 바로 독서가 시작된다.

## 3. MVP 범위

MVP는 핵심 사용자 흐름과 특수 기능 3종(★)을 단순 버전으로 구현하고, 연출·자동화·운영 기능은 학기 이후(P1·P2)로 미룬다.

**포함 (P0, 9~15주)**

- 앱 로그인 생략 (테스트 계정 자동 로그인), 관리자 권한·관리자 웹 로그인
- 목표 설정 (시간·페이지·요일·알림 시간), 온보딩, 설정 화면
- 도서 검색·등록·서재·상태 관리, 책 상세
- 타이머·페이지 기록·세션 저장
- ★ 집중 독서 모드, 목표 도달 알림
- ★ 인덱스 (페이지 + 짧은 제목)
- 완독 처리 (별점·총평)
- 캘린더·달성률·연속 독서일, 인사이트 달성률 카드, 홈 화면
- ★ 책꽂이 성장 UI·먼지털이 (단순 버전)
- 참여 유도 알림 (고정 문구)
- 관리자 웹: 대시보드·회원 관리·도서 관리

**제외**

| 단계 | 기능 |
| --- | --- |
| P1 (고도화) | 회원가입·로그인 화면, 독서 노트·모아보기, 상세 통계·리포트, 반복 미달성 시 목표 수정 안내, 먼지털이 효과·책꽂이 연출 고도화, 수동 도서 등록·표지·바코드, 관리자 알림 관리·운영 설정·공지 |
| P2 (확장) | 인덱스 공유 카드, AI 독서 회고, 고급 알림, 베타 테스트·출시 준비 |

원격 푸시는 관리자 공지(P1)에만 쓰이므로 MVP는 로컬 알림만 구현한다.

## 4. 기능 요구사항

요구사항은 8개 모듈 30개이며, 각 항목의 수용 기준을 통과하면 완료로 본다. ★는 특수 기능이다.

상태 값은 `미착수` → `진행 중` → `완료` 순서로 바꾸며, 구현 PR에서 함께 갱신한다 (AGENTS.md의 Documentation Rules 참고).

## 5. 화면 구성

앱은 하단 탭 4개(홈·서재·기록·인사이트)와 탭 밖 화면으로, 관리자 웹은 3개 메뉴로 구성한다.

| 구분 | 화면 | 주요 요소 | 관련 요구사항 |
| --- | --- | --- | --- |

## 6. 데이터 모델

MVP는 기획서 ERD 중 9개 테이블을 쓰고, Note·NotificationTemplate·AppSetting은 P1에서 추가한다. 테이블 이름은 기획서 ERD 이름(괄호 안은 DB 이름)이고, 필드는 Supabase 초기 마이그레이션 기준이다. 상세 설계는 `docs/specs/supabase-integration.md`, 근거는 결정 기록 001을 따른다.

| 테이블 | 주요 필드 | 관계 |
| --- | --- | --- |
| User (`profiles`) | id(PK, Supabase Auth 사용자), 닉네임, 이메일, 역할(user/admin), 이용 정지 여부 | 1:N UserBook, ReadingGoal |
| Book (`books`) | id(PK), ISBN(unique), 제목, 저자, 출판사, 표지, 총 페이지(관리자 정정값, 선택) | 1:N UserBook |
| UserBook (`user_books`) | user_id(FK), book_id(FK), 독서 상태, 총 페이지(사용자 입력, 필수), 현재 페이지, 시작일·완독일, 마지막 독서일 | 1:N ReadingSession, Index, DustWipeLog · 1:1 Review |
| ReadingGoal (`reading_goals`) | user_id(FK), 단위(시간/페이지), 목표량, 요일, 알림 시간, 알림 켜기 여부, 적용 시작일, 종료일 | 1:N NotificationLog |
| ReadingSession (`reading_sessions`) | user_book_id(FK), 독서 날짜(기기 로컬), 시작·종료 시각, 독서 시간, 시작·끝 페이지, 집중 이탈 횟수, 한줄평 | 1:N Index |
| Index (`book_indexes`) | user_book_id(FK, 필수), session_id(FK, 선택), 페이지, 짧은 제목, 문장(선택), 색상, 태그 | — |
| Review (`reviews`) | user_book_id(FK, unique), 별점(1~5), 총평 | — |
| DustWipeLog (`dust_wipe_logs`) | user_book_id(FK), 털어낸 시각, 먼지 단계 | — |
| NotificationLog (`notification_logs`) | goal_id(FK), 알림 종류, 발송 시각 | — |

모든 사용자 데이터 테이블은 RLS를 위해 `user_id`를 직접 가진다.

**기획서 ERD와 달라진 점**

- Book의 PK를 ISBN에서 uuid로 바꿨다. 카카오 응답의 ISBN은 `ISBN10 ISBN13` 형태이거나 비어 있을 수 있어, ISBN13을 정규화해 unique 값으로만 쓴다.
- 총 페이지는 카카오가 제공하지 않아 사용자가 입력한 값을 UserBook에 둔다. Book의 총 페이지는 관리자 정정값이자 다음 등록자의 기본값이다.
- Index는 user_book_id를 필수로, session_id를 선택으로 둔다. 책 상세에서 추가한 인덱스도 저장된다.
- NotificationLog의 "이후 독서 여부"는 저장하지 않고, 집계 시 발송 후 24시간 안에 세션이 있는지로 계산한다.

**계산값 (저장하지 않음):** 달성률, 연속 독서일, 먼지 단계, 책꽂이 배치. 매번 세션·목표 데이터에서 계산한다. 달성률·연속 독서일은 DB 함수 하나로 계산해 앱과 관리자 집계가 함께 쓴다 (결정 기록 002).

## 8. 기술 스택·시스템 구성

앱(Expo React Native)과 관리자 웹(React)이 Supabase 하나를 백엔드로 함께 쓰고, 도서 정보는 카카오 API, 알림은 기기 로컬 알림으로 처리한다.

```mermaid
flowchart LR
    App["북로그 앱<br/>Expo React Native · TS<br/>Android · iOS 사용자"]
    Supa["Supabase<br/>Auth: user / admin 역할<br/>PostgreSQL + RLS<br/>집계 RPC (admin 전용)"]
    Admin["관리자 웹<br/>React (Vite)<br/>대시보드·회원·도서 관리"]
    Kakao["카카오 책 검색 API<br/>페이지 수 미제공"]
    Noti["기기 로컬 알림<br/>참여 유도 · 목표 도달"]
    App <-- 데이터 읽기·쓰기 --> Supa
    Admin <-- 집계·관리 --> Supa
    App -- 검색 요청 --> Kakao
    App -- 예약·취소 --> Noti
```

| 영역 | 선택 |
| --- | --- |
| 앱 | Expo React Native + TypeScript (Android·iOS 동시) |
| 관리자 웹 | React + Vite + TypeScript. 같은 저장소의 `admin/` 폴더에 두고 DB 타입을 함께 쓴다. 시연은 로컬 실행 |
| 백엔드·DB | Supabase (Auth, PostgreSQL, RLS, RPC) |
| 외부 API | 카카오 책 검색 REST API |
| 알림 | 로컬 알림 (MVP). 원격 푸시는 P1 관리자 공지에서 도입 |
| 협업 도구 | VS Code, GitHub, AI 에이전트(Claude Code, Codex) |

## 10. 일정·역할 분담

**분담 원칙**

- 기본은 한인웅 = 백엔드(DB·RLS·RPC·`lib/api`), 한예찬 = 앱 프론트로 나눈다. 프론트 작업이 많아 한인웅이 일부 화면(집중 독서·책 상세·온보딩 등)과 관리자 웹을 맡는다.
- 한 사람이 맡기에 부담이 큰 기능이 생기면 두 사람이 함께 진행하고, 나눈 범위를 아래 표에 반영한다.
- 화면 파일은 한 사람이 소유한다. 다른 사람은 컴포넌트·함수를 제공하고 화면 소유자가 붙인다. 앱 골격에서 만든 화면 중 한인웅이 맡는 화면(책 상세·완독·독서 세션·종료)은 한인웅 소유로 넘어간다.

**협업 방식**

- 평일에는 각자 개발하고 본인 기기로 확인한다 (한인웅: Android, 한예찬: iOS).
- 매주 수요일 대면 개발에서 서로의 기기로 교차 확인하고, 아래 접점을 합의한다. 시연은 Android 실기기 기준이다.
